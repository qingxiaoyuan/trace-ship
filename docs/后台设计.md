# 后台设计文档（Python Django + DRF）

## 一、设计目标

为软件版本发布管理系统提供统一后端服务，支撑项目接入、代码仓库管理、提交规范审查、TAG 生成与发布、系统内置打包（Docker 镜像 / 本地脚本 / SVN 推送）、工作流审批、发布看板、站内通知、使用反馈等能力。

---

## 二、技术选型

| 层级 | 技术 | 版本建议 | 说明 |
|-----|------|---------|------|
| 开发语言 | Python | 3.11+ | 开发效率高，AI 生成代码质量好 |
| Web 框架 | Django | 5.x | 自带 ORM、Admin、认证、迁移 |
| API 框架 | Django REST Framework | 3.15+ | RESTful API 快速开发 |
| 数据库 | PostgreSQL | 16+ | 跨平台、JSON 字段支持好 |
| 缓存/会话 | Redis | 7+ | 缓存、分布式锁、Celery 消息代理 |
| 任务队列 | Celery + Redis | 5.x | 异步任务、定时任务 |
| 工作流 | 自研审批链引擎 | - | 基于 `node_config` 审批链配置驱动，graph_data 自动生成用于只读流程图渲染 |
| 认证 | django-auth-ldap + JWT | - | 对接 LDAP/AD（「系统配置」页面 ldap_* 键优先，环境变量兜底），本地应急管理员并存 |
| 外部集成 | GitProvider 适配器（GitLab）/ ldap3 / subprocess(svn) / Docker / Nexus API | - | Git 仓库、LDAP、SVN 产物推送、镜像打包 |
| 容器化 | Docker + Docker Compose | - | 一键部署 |

```
├── manage.py
├── requirements.txt
└── Dockerfile
```

> 说明：
> - 旧的 `integrations`（项目外站绑定）、独立 `commit`、`dashboard`、`ai` 应用均未落地或已合并：
>   提交审查并入 `apps.repository`，看板统计挂在 `apps.release` 的 `dashboard/*` 接口下，
>   后端暂无 AI 调用模块（AI 能力由 vscode-commit 插件承担）。
> - `apps.jenkins` 已整体下线（模型、服务、API、`python-jenkins` 依赖均已移除），
>   仅在 `INSTALLED_APPS` 中保留迁移 tombstone 以维持迁移链，打包统一走 `apps.package`。

## 五、核心模块设计

### 5.1 认证与权限

- LDAP 登录：`django-auth-ldap` 配置 LDAP 后端，首次登录自动创建本地用户。
  - LDAP 连接参数支持两种来源：「系统配置」页面（`sys_config` 的 `ldap_*` 键，含 `ldap_enabled` 开关、
    服务地址、Bind DN/密码、搜索基准 DN、用户过滤器、TLS 证书策略与 CA 证书）优先，环境变量 `LDAP_*` 兜底。
  - 登录时由 `apps.account.ldap_config` 动态应用页面配置；系统配置页提供 LDAP 连接测试接口。
- 本地应急账号：超级管理员可创建 `source=local` 用户；默认管理员 `admin / admin@123`，
  密码丢失可用 `python manage.py reset_admin_password`（支持 `--username` / `--password`）恢复。
- JWT：`djangorestframework-simplejwt` 提供 Token。
- 权限校验：
  - 超管：直接放行
  - 项目内权限：通过 `ProjectMember.role` 判断
  - 功能权限：Django 内置权限 + 自定义 permission 类

### 5.2 项目管理

- 项目 CRUD 仅超管或项目管理员可操作。
- 项目成员维护：项目管理员可添加/移除/修改角色。
- 项目创建时自动补齐内置发布审批流程（WorkflowDefinition）。
- 项目停用后禁止新增发布。

### 5.3 凭证管理

- 统一凭证模型 `sys_credential`，所有外部系统访问钥匙集中管理。
- 支持两种认证模式：
  - `token`：GitLab Token
  - `password`：SVN 用户名密码 / LDAP Bind Password
- 凭证归属用户（`owner`），用户可创建个人凭证并在项目中复用。
- `svn_password` 类型为全系统共享凭证：所有登录用户可见可用，用于打包产物 SVN 推送。
- 凭证内容使用 Fernet（AES）加密存储，主密钥 `CREDENTIAL_SECRET_KEY` 独立配置。
- 使用记录审计：`last_used_at` + 操作日志；删除前校验是否被引用。
- 凭证解析统一走 `utils.provider.credential_resolver.resolve_credential(source, request_user)`。

### 5.4 项目外站绑定（已废弃）

> 早期设计通过 `sys_project_integration` 实现项目与外部站点（Git/SVN/Jenkins）的统一绑定，
> 并支持 `current_user / specified_user / fixed / global` 四种凭证使用模式。
> 该设计未落地且已废弃：当前代码仓库（`sys_repo`）直接归属项目并各自绑定凭证，
> 凭证来源仅区分 `personal`（个人）/ `project`（项目）两种模式；
> SVN 不作为代码仓库，仅在打包配置中作为产物推送目标；Jenkins 集成已整体下线。

### 5.5 仓库管理（GitProvider 适配器）

#### 5.5.1 Provider 抽象层

代码位于 `utils/provider/`，Git 类 provider 统一提供分支、提交、tag、MR、compare、create tag 等能力；
当前仅实现 GitLab，工厂函数为 `get_provider(vendor, server_url, credential_data)`：

```python
from utils.provider.factory import get_provider
from utils.provider.credential_resolver import resolve_credential

# 访问仓库时先解析凭证，再创建 provider
credential_data = resolve_credential(repository, request_user)
provider = get_provider(repository.vendor, server_url, credential_data)
branches = provider.list_branches(repository.external_identity)
```

#### 5.5.2 GitLab 实现

基于 `python-gitlab`，支持分支/提交/tag/MR 拉取、compare、创建 tag、连通性测试等。
新增平台（Gitea/GitHub/Gitee）时按同一抽象扩展 Provider 实现类即可。

#### 5.5.3 分支同步

- 「同步分支」（`sync-branches`）从远端拉取分支及最新提交信息落库到 `sys_repo_branch`；
- 分支列表接口优先读本地，本地无数据时自动从远端同步一次。

#### 5.5.4 SVN

- SVN 不作为代码仓库接入；SVN provider 仅用于打包产物推送（见 5.8 打包）。

### 5.6 提交记录审查

- 拉取 commit 后解析 `message`，按规范提取：
  - 变更类型（有/无配置项改动）
  - 更新内容（A/F 标记）
  - 配置项改动（INI 格式）
  - 关联性改动（各模块版本）
- 不合规项标记 `review_status=warning/illegal`，并给出原因；支持人工复核与按 tag 范围拉取审查（review-range）。
- 合规率统计：`/api/repositories/compliance-stats/` 按项目统计 pass/warning/illegal/unreviewed 数量。
- 审查基于规则引擎，后端暂无 AI 审查能力（AI 生成规范 commit 信息由 vscode-commit 插件承担）。

### 5.7 TAG 生成与发布

当前发布流程以“审批通过后推 tag”为主，打包统一由 `apps.package` 承担：

1. **创建发布**（`ReleaseService.create_release`）：校验项目状态、发布周期规则与 tag 后缀；
   未传版本号时基于仓库已有 tag 和 `Project.version_rule` 自动计算，rc/beta 类型自动补后缀并统一拼接日期段。
2. **变更预览**（`preview_changes`）：拉取上个 tag 到目标分支之间的 commits / MRs，解析 A/F 类更新内容。
3. **发布说明**（`generate_doc` / `update-doc`）：生成并保存 Markdown 发布说明（2 列表格），支持人工编辑，
   支持导出 Markdown / PDF / Word（`export-md` / `export-pdf` / `export-word`）。
4. **提交审批**（`submit_audit`）：要求发布处于 `draft` 且发布说明非空；按发布类型查找启用的
   `WorkflowDefinition`，创建 `WorkflowInstance`，状态改为 `pending`。
5. **审批流转**：`WorkflowEngine` 根据 `node_config` 生成任务，支持通过、驳回、转交、回退、撤销。
6. **审批完成**（`handle_workflow_completed`）：调用 `push_tag`；推 tag 成功状态变为 `released`，
   失败变为 `rejected` 并写入 `rejected_reason`。
7. **自动打包**：推 tag 成功后调用 `PackageService.trigger_auto_packages_for_release`，
   为开启 `auto_package_on_release` 的 `PackageConfig` 创建 `PackageTask`；触发异常仅记录操作日志，不影响发布状态。
8. **审批驳回**（`handle_workflow_rejected`）：状态改为 `rejected`；回退到初始节点时可恢复为 `draft` 并解除流程实例关联。

发布校验规则：

- 发布类型为 `formal` / `rc` / `beta`（取代旧的 formal/test）；
- 分支规则、tag 后缀规则由项目 `release_rule` / `version_rule` 控制；
- 正式发布需满足发布周期规则（`validate_release_cycle`）。

### 5.8 打包（apps.package）

打包统一由 `apps.package` 执行，镜像可来自本地 Docker 或 Nexus（Nexus 连接在「系统配置」页面维护，
存 `sys_config` 的 `nexus_*` 键）：

1. 「打包镜像」页面实时聚合本地与 Nexus 镜像列表，支持上传 tar 包导入本地（`docker load`，`images/import`）。
2. 项目管理员在「打包配置」中选择镜像（按坐标 get_or_create 镜像记录）、构建目录、产物目录，
   可选填写自定义脚本、环境变量、发布后自动打包开关与 SVN 推送配置。
3. 打包任务（Celery 异步执行）流程：
   - 准备 `workspace/{source,artifacts,tmp}`；
   - `git clone` 源码到 `workspace/source`；
   - 只挂载 `source` / `artifacts` / `tmp` 到容器 `/workspace` 对应目录，`scripts` / `deploy` 使用镜像自身内容；
   - 容器内工作目录为 `/workspace/source`，通过环境变量传入 `DEPLOY_DIR`、`SCRIPTS_DIR` 等；
   - 统一以 `--entrypoint /bin/sh` 启动，镜像自身 ENTRYPOINT 不生效；
   - 若配置 `custom_script`，则以 `sh -c` 直接执行该脚本；否则执行镜像内置 `script_entry`（默认 `/workspace/scripts/pack.sh`）；
   - 打包产物写入 `/workspace/artifacts`；扫描产物，可选推 SVN（支持事后手动 `push-svn`）。
4. 任务状态：`queued / running / success / failure / canceled`，支持取消、查看日志、下载产物。
5. 镜像接入规范：镜像内提供 `/workspace/scripts/pack.sh`（内置打包入口）、可选 `/workspace/deploy`
   （预制依赖）、容器内存在 `/bin/sh`；入口脚本不主动联网安装依赖。

### 5.9 工作流引擎（自研审批链）

#### 5.9.1 流程定义

流程定义保存 `node_config` 审批链配置（节点列表），`graph_data` 由 `node_config` 自动生成，
仅用于前端只读流程图渲染。

#### 5.9.2 审批模式

每个审批节点生成一个或多个 `WorkflowTask`，节点 `mode` 决定通过条件：

| 模式 | 说明 |
|------|------|
| any（或签） | 任一审批人通过即流转 |
| all（会签） | 全部审批人通过才流转 |

#### 5.9.3 支持的审批动作

- approve：通过，流转到下一节点
- reject：驳回，流程实例标记 rejected
- transfer：转交给他人，不流转
- rollback：回退到指定历史节点，重新生成任务（回退到初始节点时业务单据可恢复 draft）
- revoke：发起人撤销，流程实例标记 revoked

#### 5.9.4 审批人解析

节点配置中定义审批人类型：

```json
{
  "type": "leader/role/user/self",
  "value": ["user_id 或 role_id"],
  "mode": "any/all"
}
```

- `leader`：项目负责人；`role`：项目内指定角色成员；`user`：指定用户；`self`：发起人。

#### 5.9.5 流程进度回显

返回实例 `graph_data` + `node_status` 节点状态快照，前端据此渲染流程图节点颜色。

### 5.10 发布看板

- 看板统计接口挂在发布模块下：`/api/releases/dashboard/overview|trend|projects`，
  聚合发布次数、成功率、待审批数、发布趋势与项目维度统计。
- 发布记录支持多维度筛选与发布目录（`/api/releases/catalog/`，按正式/RC/Beta 分类）。

### 5.11 AI 接入（后端暂未实现）

- 后端暂无 AI 调用模块（无 ai app、无 ai_invoke_log 表），提交审查基于规则引擎。
- AI 能力目前由 `vscode-commit/` VS Code 规范提交助手插件承担：默认本地 DeepSeek 接口，
  `commit.apiProtocol` 配置（auto / openai / anthropic）兼容 OpenAI / Anthropic 等更多 AI 服务。
- 后续如需后端 AI 能力（发布说明生成、风险识别等），建议新增统一 AI 客户端封装并记录调用日志。

### 5.12 站内通知

- `apps.notification` 提供站内通知，类型覆盖审批（audit）、构建结果（build）、发布结果（release）、系统（system）。
- 支持未读数、标记已读/全部已读、清除等操作。

### 5.13 使用反馈

- `apps.feedback` 收集功能建议、问题反馈与体验优化意见，全员可提交、查看、点赞。
- 删除仅限本人或超级管理员；超管可将反馈标记为已处理（记录处理人与处理时间），
  状态流转：`open`（待处理）→ `processed`（已处理）。

## 九、安全设计

### 9.1 凭证加密存储

- 所有外部系统凭证（Token、密码）必须加密后落库，禁止明文存储。
- 加密方案：AES-256-CBC 或 Fernet（`cryptography` 库）。
- 主密钥 `CREDENTIAL_SECRET_KEY` 独立配置，不写入代码仓库，通过环境变量注入。
- 主密钥定期备份，丢失后所有凭证无法解密。
- 凭证在内存中解密后应尽快使用，避免日志泄露。
- 接口返回时凭证内容必须脱敏，仅展示前 4 位 + "****" + 后 4 位。

示例代码：

```python
# utils/crypto.py
from cryptography.fernet import Fernet
from django.conf import settings
import json

_fernet = Fernet(settings.CREDENTIAL_SECRET_KEY.encode())

def encrypt_credential(data: dict) -> str:
    return _fernet.encrypt(json.dumps(data).encode()).decode()

def decrypt_credential(encrypted: str) -> dict:
    return json.loads(_fernet.decrypt(encrypted.encode()).decode())
```

模型中使用：

```python
# apps/credential/models.py
class Credential(models.Model):
    encrypted_data = models.TextField()

    def set_data(self, data: dict):
        self.encrypted_data = encrypt_credential(data)

    def get_data(self) -> dict:
        return decrypt_credential(self.encrypted_data)
```
