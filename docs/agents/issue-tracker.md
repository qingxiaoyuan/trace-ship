# 事项管理：GitHub Issues

本仓库的 Matt 技能统一在 [qingxiaoyuan/trace-ship 的 GitHub Issues](https://github.com/qingxiaoyuan/trace-ship/issues) 管理需求、规格、实施任务和进度。

## 操作约定

- 技能要求发布规格或创建任务时，创建 GitHub Issue；要求读取事项时，读取对应 Issue 的正文、状态、标签和评论。
- 优先使用 GitHub 连接器；能力不足时使用 `gh`，显式指定 `--repo qingxiaoyuan/trace-ship`。多行正文使用临时文件与 `--body-file`。
- 创建前检索已有事项，优先更新同一事项，避免重复创建。更新前读取最新正文，保留用户改动。
- 规格正文在 Issue 中维护，后续实施任务关联该规格 Issue。支持时使用子事项和依赖关系，否则在正文使用 `Part of #编号`、`Blocked by #编号` 和任务清单。
- 决策、阻塞、验证结论和完成状态更新到对应 Issue。仅在任务实际完成后关闭；待确认规格保持草稿语义。
- `.scratch/` 不再作为事项管理目录。仓库中的术语、ADR、接口与使用文档继续随代码维护；迁移完成后删除本地过程文件，在 docs/README.md 集中保留 Issue 入口。
- 迁移先创建并回读 Issue，确认正文完整后，再删除本地事项和规格文件，更新索引及引用。迁移失败时保留原文，并明确标记迁移未完成。
- 标签使用 [中文标签映射](triage-labels.md)，将 Matt 的英文角色转换成 GitHub 中文标签。

## 文档与事项分工

- 规格 Issue 维护问题、解决方案、用户故事、实施决策、测试决策、范围外内容和待确认项；日常决策更新正文，讨论与证据留在评论或 PR。
- 任务经拆分确认后创建关联子 Issue，交付内容覆盖完整可验证行为，并记录依赖。未确认的历史规格不自动标为「可由AI开发」。
- GLOSSARY.md 维护术语；重要长期取舍保留在 docs/adr/，Issue 链接对应 ADR。API、接入指南和原型资源继续随代码维护。
- 旧规划放历史归档 Issue，明确过时内容及状态；归档关闭不等于功能完成。源文档的历史快照放折叠附录，避免丢失原始需求编号和决策依据。
- 已迁移事项见 [文档索引](../README.md)，不另设一套本地进度表。

## 标题与正文标准

标题用中文描述具体对象和行为或故障，例如「创建正式草稿时选择 RC 并锁定来源提交」。保持简短，不添加阶段、优先级、负责人或 `[规格草稿]` 等状态前缀；状态由标签和正文表达。这是本仓库的标题约定，Matt 本身只要求简短、描述清楚。

- 功能规格使用 [规格模板](../../.github/ISSUE_TEMPLATE/spec.md)：问题陈述、解决方案、用户故事、实施决策、测试决策、范围外、补充说明七部分。
- 开发任务使用 [任务模板](../../.github/ISSUE_TEMPLATE/task.md)：父事项、要实现的行为、验收条件、前置依赖。没有父事项时省略父事项段；设置原生依赖后可省略正文依赖段。
- 原始缺陷使用 [缺陷模板](../../.github/ISSUE_TEMPLATE/bug.md)。这是本仓库补充的采集格式；分流时验证复现、范围和预期，再整理为可接手的任务。
- 用户故事覆盖实际使用场景；验收条件写成可观察的行为。任务尽量跨必要的数据、API、界面与测试层，完成后可独立演示或验证，规模适合一次新的开发会话。
- 正文维护最新结论，评论记录讨论、阻塞和证据；规格与任务避免依赖具体文件路径、行号和实现片段，精确表达决策的原型片段可以保留。历史附录不作为当前实现指令。
- 手工创建的 Issue 默认「待评估」；技能生成且已完成确认的规格或任务按标签映射直接标「可由AI开发」。模板默认状态不覆盖已完成的确认。

## 开发与交付流程

以下分支与 PR 约定是本仓库在 Matt 规格、任务、TDD 和审查流程上的交付规则。

1. **需求明确**：用 grill-with-docs 核对代码、澄清规则；领域术语与重要架构取舍同步进入术语表/ADR。to-spec 在测试边界确认后将结论整理为规格 Issue。简单改动可在一个 Issue 内完成，不强制拆分。
2. **任务准备**：复杂需求经 to-tickets 拆成可验证的端到端任务；用户确认粒度和依赖后创建子事项。优先选择前置任务均已完成的任务，记录负责人。
3. **任务分支**：开始产品代码实现前检查工作区与已有分支，保留用户改动。默认每个独立开发任务从更新后的默认分支 master 创建 `codex/issue-<编号>-<英文短名>` 分支；沿用属于同一任务的已有分支，不重复创建。需求访谈不必先建代码分支。
4. **实现与验证**：implement 读取 Issue 最新正文、评论和依赖，在已确认的测试边界实施 TDD，执行相关检查与代码审查。出现范围变化先更新规格与验收，不把新需求悄悄塞进当前任务。
5. **提交与 PR**：用户授权提交和推送后，创建关联开发任务的 PR，默认目标 master。说明行为变化、验证证据和影响。创建 PR 的授权不等于合并或部署授权。
6. **验收与关闭**：达到验收条件的开发任务可在 PR 正文写 `Closes #任务编号`；合入默认分支后 GitHub 自动关闭该任务。仍需合并后或外部环境验证时，用普通关联文字代替关闭关键字，验证完成后再关闭。父规格使用 `Refs #规格编号`，仅在必要子任务完成、整体行为验收通过后关闭，拆任务和单个子 PR 均不代表父规格完成。
7. **后续工作**：验收发现的新缺陷或范围外需求另建关联 Issue。部署是单独操作，须有明确授权；Issue 关闭不自动触发部署。

本仓库当前默认分支为 master，开始交付时重新核对远端配置。依赖任务默认等前置 PR 合并后再开分支；确需并行或集成分支时，明确基线与最终集成 PR，目标不是默认分支的 PR 不依赖 `Closes` 自动关闭事项。

参考：[GitHub PR 与 Issue 关联及自动关闭规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。
