# 产品、仓库复用与仓库级版本发布需求

## 1. 文档信息

- 状态：已确认，实施中
- 核心结论：现有 `Project` 就是产品；软件最小单位是仓库；产品只负责关联和配置仓库；发布与版本始终属于单个仓库。
- 明确排除：不建设“产品组合发布”、产品级版本、产品版本清单或一次审批同时发布多个仓库。

## 2. 背景与问题

系统原先把仓库直接归属到项目，实际使用中出现了偏移：落库对象是一个个物理代码仓库，而同一仓库可能被多个产品复用。

典型场景包含四个仓库：上位机、后台、Web、中台。

- Web 应用产品使用 Web、后台、中台三个仓库。
- 对外 SDK 产品使用中台、上位机两个仓库。
- 中台仓库只登记一次，被两个产品分别关联和配置。

原模型会导致重复登记仓库、凭证和版本信息，且任一产品修改仓库基础信息时可能影响其他产品。另一方面，产品只是配置和权限边界，并不等同于一个需要单独发布版本的代码实体。

## 3. 目标与非目标

### 3.1 目标

1. 仓库成为全局唯一的软件资源，可被多个产品复用。
2. 现有 `Project` 直接承担产品语义，不新增平行的 Product 模型。
3. 产品可以手动关联、配置和停用仓库，不复制仓库基础数据。
4. 每次发布只针对一个产品上下文中的一个仓库，继续使用现有审批与推 Tag 流程。
5. 仓库 Tag 和仓库版本全局唯一，不因产品复用而复制版本序列。
6. 打包配置归属产品与仓库的关联关系，允许同一仓库在不同产品下使用不同构建参数。
7. Git 凭证保持个人凭证借用模式，授权范围明确到仓库、产品、操作和有效期。
8. 保留全部存量项目、仓库、发布、审批、打包和凭证数据，不改变历史记录含义。

### 3.2 非目标

以下能力不属于本需求，界面、接口和数据模型中均不应出现：

- 产品组合发布。
- 一次发布同时冻结或操作多个仓库。
- 产品级版本号或产品版本自动计算。
- 产品版本不可变清单及清单摘要。
- 多仓库全量预检、部分失败和失败项重试状态机。
- 产品快照 Tag。

## 4. 领域模型

### 4.1 产品 `Project`

`Project` 在业务文案中表示产品，继续保留现有类名、表名、主键和 API，以避免破坏存量数据与外部调用。

产品负责：

- 产品名称、负责人、成员和权限。
- 发布规则与审批流配置。
- 关联哪些仓库。
- 每个关联仓库在本产品内的名称、默认分支、源码子目录和构建配置。

产品不拥有物理仓库，也不产生独立的产品版本。

### 4.2 仓库 `Repository`

仓库是软件和版本管理的最小单位。

- 物理仓库按 `vendor + server_url + external_identity` 全局唯一。
- 仓库基础信息、分支、Commit、Tag、健康状态和同步时间只保存一份。
- 仓库版本规则独立维护；登记时可从产品规则复制一次，之后不再运行时回退。
- `Repository.project` 仅作为存量兼容字段，新逻辑不得把它当作唯一产品归属。
- 仓库详情展示所有使用该仓库的产品，但不同产品的私有配置互不覆盖。

### 4.3 产品仓库关联 `ProductComponent`

产品与仓库通过显式关联模型连接。

| 字段 | 说明 |
| --- | --- |
| `project` | 所属产品 |
| `repository` | 被引用的物理仓库 |
| `component_code` | 产品内配置键 |
| `display_name` | 产品内展示名称 |
| `default_branch` | 产品使用该仓库时的默认分支 |
| `source_subdir` | 可选源码子目录 |
| `product_config` | 产品内非敏感配置 |
| `sort_order` | 展示顺序 |
| `is_active` | 是否启用 |

同一仓库可以关联多个产品。同一产品如确有多个构建角色，可通过不同 `component_code` 引用同一仓库；发布时仍一次只选择其中一个仓库上下文。

### 4.4 仓库发布 `ReleaseRecord`

现有 `ReleaseRecord` 继续作为唯一发布主记录。

- `project` 表示本次发布所属产品上下文。
- `repository` 表示本次实际发布的软件仓库。
- `version` 和 `tag_name` 均为仓库版本，不是产品版本。
- 一次发布只创建一个仓库 Tag，只进入一条审批流程。
- 状态保持 `draft`、`pending`、`released`、`rejected`。
- 已有发布记录、ID、详情链接和审批关联保持不变。

### 4.5 打包配置 `PackageConfig`

打包配置归属 `ProductComponent`，同时保留 `project`、`repository` 作为兼容和查询冗余字段。

因此同一物理仓库可以在 Web 应用和 SDK 产品下使用不同镜像、脚本、环境变量、产物目录和 SVN 推送目标。仓库发布成功后，只触发本次 `project + repository` 对应的自动打包配置，不得跨产品触发。

### 4.6 凭证授权

仓库访问继续使用个人凭证，不改成全员共享服务凭证。

产品获得仓库凭证的方式是：仓库所有者必须已是该产品成员，然后才能把该仓库关联进产品。仓库绑定的 Token 必须属于仓库所有者。关联成功后，该产品的发布、同步和打包使用这份凭证。

- 任何使用者都不能查看凭证明文。
- 系统记录实际操作人、出借人（所有者）、产品、仓库、操作类型、结果和失败原因。
- 显式借用表仅作补充审计，不是关联或发版本的前提。

## 5. 用户流程

### 5.1 登记仓库

1. 仓库管理员从全局仓库页登记物理仓库。
2. 登记仓库不要求绑定产品。
3. 系统校验物理仓库唯一性，避免同一远端仓库重复落库。
4. 仓库登记完成后可由不同产品分别关联。

### 5.2 配置产品

1. 创建或打开产品。
2. 在“产品组件”页选择“关联已有仓库”。
3. 设置产品内名称、默认分支、源码子目录等配置。关联前必须先把仓库所有者加入产品成员。
4. 如需构建，在该产品组件下维护打包配置。

### 5.3 发布仓库

1. 选择产品。
2. 仅展示该产品已启用关联的仓库。
3. 选择一个仓库、发布分支和仓库发布类型。
4. 按仓库 Tag 计算下一仓库版本，预览上一个仓库 Tag 到目标分支的变更。
5. 使用该仓库所有者已授权给本产品的个人凭证。
6. 生成发布说明并提交一条审批。
7. 审批通过后只为该仓库创建 Tag。
8. 只触发该产品与仓库关系下启用的自动打包配置。

## 6. 版本与 Tag 规则

### 6.1 版本归属

- 版本属于仓库，不属于产品。
- 同一仓库被多个产品使用时，共享同一套 Tag 和版本序列。
- 产品页面显示各关联仓库最近一次在该产品上下文中成功发布的版本，仅作汇总展示。
- 产品本身不计算“下一产品版本”。

### 6.2 发布基线

- 下一版本计算基于目标仓库中匹配版本规则的 Tag。
- 变更预览基于目标仓库的上一个匹配 Tag 与本次目标分支。
- 其他产品发布同一仓库后会产生新的仓库 Tag，这是仓库真实版本演进的一部分，不做产品级基线隔离。

### 6.3 Tag 命名

继续使用仓库现有版本规则，例如：

```text
VA.5.1.0_20260909
VA.5.2.0-beta_20260909
VA.5.2.0-rc_20260909
```

禁止生成产品组合 Tag 或用产品版本覆盖仓库版本。

## 7. 功能需求与验收标准

### 7.1 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PRV-DOM-01 | 仓库为全局唯一资源，可被多个产品关联 | P0 |
| PRV-DOM-02 | 产品通过 `ProductComponent` 手动关联和配置仓库 | P0 |
| PRV-DOM-03 | 全局登记仓库时不强制选择产品 | P0 |
| PRV-REL-01 | 发布只允许选择一个产品关联仓库 | P0 |
| PRV-REL-02 | 发布、审批、Tag 和重试继续使用 `ReleaseRecord` 流程 | P0 |
| PRV-VER-01 | 版本和 Tag 归属仓库并全局共享 | P0 |
| PRV-CRED-01 | 仓库所有者加入产品成员后，该产品才能关联仓库并使用其个人凭证 | P0 |
| PRV-CRED-02 | 绑定凭证必须属于仓库所有者；使用过程完整审计且不暴露明文 | P0 |
| PRV-PKG-01 | 打包配置归属产品组件 | P0 |
| PRV-PKG-02 | 自动打包不得因共享仓库跨产品触发 | P0 |
| PRV-MIG-01 | 存量仓库、发布、审批、打包和凭证数据原义保留 | P0 |
| PRV-NEG-01 | 系统中不存在产品组合发布入口、模型和 API | P0 |

### 7.2 验收场景

#### 场景一：共享仓库

1. 中台仓库只登记一次。
2. Web 应用和 SDK 均可关联中台仓库。
3. 两个产品可以配置不同默认分支、展示名称和打包参数。
4. 停用任一产品下的中台关联，不影响另一个产品。

#### 场景二：仓库级发布

1. 从 Web 应用选择中台仓库发起发布。
2. 一次发布只展示和操作中台仓库。
3. 审批通过后只创建一个中台 Tag。
4. 发布看板记录产品为 Web 应用、软件为中台仓库。

#### 场景三：凭证借用

1. 中台仓库所有者加入 Web 应用后，Web 应用可关联中台并发布。
2. Web 应用成员可以使用该仓库凭证，但不能查看 Token。
3. 所有者尚未加入 SDK 时，SDK 不能关联或使用该仓库凭证。
4. 所有者加入 SDK 并完成关联后，SDK 才能在自己的产品上下文发布中台。

#### 场景四：打包隔离

1. Web 应用和 SDK 为中台仓库分别配置自动打包。
2. 在 Web 应用上下文发布中台后，只触发 Web 应用的配置。
3. SDK 的打包任务和产物不受影响。

#### 场景五：存量兼容

1. 迁移前的项目、仓库、发布、审批和打包任务仍可查询。
2. 历史 `ReleaseRecord` 不被改写或转换成其他发布模型。
3. 原仓库凭证不自动扩大到新关联产品；新产品必须先把所有者拉进成员再关联。
4. 迁移失败可以回滚应用版本，旧数据无需恢复脚本。

#### 场景六：负向验证

1. 侧边栏、产品详情和发布页没有“组合发布”入口。
2. 前端没有 `/product-releases` 路由。
3. 后端没有 `/api/releases/products/` API。
4. 数据模型中没有 `ProductRelease`、`ProductReleaseItem` 或产品组合发布开关。

## 8. 迁移与发布计划

### 8.1 数据兼容

采用新增关系、回填、双读、切换的顺序：

1. 新增 `ProductComponent`，按现有 `Repository.project_id` 回填产品仓库关系。
2. `Repository.project` 改为可空并保留，暂不删除历史字段。
3. 新增产品组件级 `PackageConfig.product_component`，按原 `project + repository` 回填。
4. 新增凭证借用与审计表，把原仓库凭证授权范围限定为原产品。
5. 仓库和提交查询兼容旧字段与新产品组件关系。
6. 不迁移、不复制、不合并任何 `ReleaseRecord`。

### 8.2 上线前检查

- 执行 `python manage.py check_product_repository_consistency --json --strict`。
- 重复物理仓库只生成报告，不得在普通迁移中自动合并。
- 人工确认主仓库后，使用专用命令先 dry-run，再显式 `--apply`。
- 核对每个存量仓库都存在原产品的组件关联。
- 核对每个打包配置都指向一致的产品组件。
- 核对借用授权未扩展到新关联产品。

### 8.3 实施阶段

第一阶段完成领域兼容：全局仓库、产品组件、产品内配置、凭证借用和打包配置回填。

第二阶段调整现有仓库级发布：产品筛选仓库、借用授权选择、审批与自动打包隔离。

第三阶段在至少一个稳定发布周期后评估删除 `Repository.project`、`CommitRecord.project` 等兼容字段。历史 `ReleaseRecord` 永久保留，不引入替代发布模型。

### 8.4 风险控制

- 不删除或覆盖存量发布、审批、Tag、提交与打包记录。
- 不静默合并重复仓库。
- 不自动扩大个人凭证借用范围。
- 共享仓库发布只触发当前产品的打包配置。
- 任何清理兼容字段的迁移单独评审和发布。
