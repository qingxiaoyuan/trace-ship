# 0012 - 发布文档审查整改闭环与修改后同步替换 SVN 文档

**状态:** proposed
**日期:** 2026-08-18
**决策者:** 产品/研发团队
**关联规格:** 无（来自「质量/提交审查」页对已发布版本文档的审查整改与文档一致性维护需求）

## 背景

审查员对已发布版本的发布文档只能查看、无法提出整改意见；且打包产物推送过 SVN 后，
修改发布文档不会同步到 SVN 目录中的文档文件，造成版本目录内文档与系统内发布文档不一致。
需要提供审查整改闭环，并在修改文档时同步替换已推送 SVN 的文档。

## 决策

1. **审查整改闭环**（入口位于「质量/提交审查」页的「已发布回溯」板块，按三 Tab 切换
   「变更文档 / 版本提交 / 审查整改」）：
   - 系统审查员（拥有 `release.audit` 权限或超管）可对已发布（`released`）版本的发布文档
     逐条发起整改意见；每条意见独立判定，状态机 `open`（待整改）→（发布人回复）
     →`replied`（待复核）→（审查员通过）→`resolved` 或（驳回+可选备注）→`open` 可多轮；
   - 仅发布人 `publisher` 可回复并修改发布文档；通过/驳回仅意见发起人（或超管）；
   - 全部意见 `resolved` 即整改完成；全程站内通知（`review` 类型）推动双方。
2. **提交记录区间展示**：发布详情与提交审查页展示「上一 tag -> 本次发布 tag」区间内
   **已保存的提交快照**（`release_commits`，生成发布说明时持久化），不依赖实时拉取；
   `ReleaseRecord.base_tag` 在生成发布说明时持久化基线 tag，历史数据为空时降级显示
   「首个版本区间」。
3. **修改文档同步替换 SVN 文档**：`update-doc` 保存成功后，自动将发布文档同步替换到
   该发布**所有已成功推送过 SVN** 的打包任务目录（`release-{version}.md`）：
   - 基于 SVN `checkout` 版本目录（`--depth files`）→ 覆盖文档 → `commit`，按目录并行执行；
   - 远程文档内容与本地一致时跳过 `commit`（避免“no changes”误报失败）；
   - **任一目录失败不阻塞文档保存**：前端提示失败详情（任务名/地址/原因），并记入操作日志。

## 影响与兼容性

- 整改仅面向 `released` 发布，期间发布状态不变；与既有发布前审批工作流相互独立。
- 提交记录为发布时快照，发布后新增提交不会回填。
- SVN 同步依赖已有 `config_snapshot` 与 `stage_info.svn_push` 记录，历史已推送任务可被定位；
  未推送过 SVN 的发布不受影响。
- 新增迁移 `release.0010`（`base_tag` + 整改模型）；`Notification.TYPE_CHOICES` 追加 `review`。
