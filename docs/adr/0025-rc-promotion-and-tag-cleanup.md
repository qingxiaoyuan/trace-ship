# 0025 - 正式发布固定来源 RC，标签清理与发布历史分离

## Status

accepted，2026-10-09。用户已确认[规格 #5](https://github.com/qingxiaoyuan/trace-ship/issues/5)的建议基线与测试边界。决策接受不代表全部实现；实施与验收按关联任务 #12–#18 推进。

## Context

正式发布需基于测试过的 RC 代码，但继续采用独立的正式版本号；同一 RC 可以产生多个正式版。RC 标签积累需要手动清理，而现有源码获取依赖标签，平台删除版本还可能级联删除打包历史。

## Decision

采用固定提交与来源快照表达正式版的代码身份，将远端标签生命周期与平台发布记录生命周期分离。清理只移除标签，保留来源关系；通过仍存在且提交一致的正式引用获取已清理 RC 的代码，执行构建前核验提交。

版本归属继续遵守 ADR-0020 的物理仓库边界，名称使用 ADR-0021 的项目口径。审批和打包继续使用既有模块与独立生命周期。

按本决策实施时，ADR-0015 的标签删除能力增加跨入口引用保护；其“版本计算仅依赖远端”的前提改为同时保留已发布历史编号依据。正式版标签与 RC 标签不做重命名替换。

正式累计说明以提交身份定义区间：基线是同物理仓库中低于目标正式版本的最高正式版本，平台已发布历史快照优先于同名远端 Tag；首次生成后冻结基线名称与 SHA。首发累计全部可达历史，同 SHA 允许无新增代码，非祖先基线须另行处理回滚/分叉。GitLab 提交接口按 revision range 完整分页；MR 仅以区间内的合并或 squash 提交作为纳入证据，证据缺失显示提示，外部故障不伪装成空区间。人工说明不改变系统身份。

版本占用以物理仓库、发布类型、主次修订号唯一，不包含日期和项目；成功后保留已消费记录，审批终止释放，推 Tag 失败保留供重试。原申请的远端 Tag 注释标记和 SHA 共同作为未知结果对账证据。迁移仅为当时已经进入审批的历史正式申请设置可信兼容标记，客户端不能写入该标记。

正式发布必须有非空流程和有效审批人；稳定性由配置的人工审批确认。仓库锁统一协调提交、任务创建、引用删除和清理；执行构建前再次核验实际 HEAD，不能用选择候选时的校验替代。远端操作无法与数据库原子提交，清理先写尝试记录再操作，重试区分已确认的平台删除与无法归属的远端缺失。

## Consequences

- Tag 数量可以减少，同时保留审批和代码来源；同 RC 可多次晋升。
- 需要保存来源与清理元数据，保护最后一个有效引用，并处理远端操作与本地记录部分成功。
- 拉取引用与版本显示分开后，自定义打包脚本不能假定已清理的 RC Tag 仍存在；重打包只保证代码提交身份。
- 平台不能阻止所有外部 Tag 改写，必须在后续使用时重新验证。

## Alternatives

- 永久保留所有 RC Tag：实现最少，但不能解决用户提出的标签管理问题。
- 删除 RC 发布记录与 Tag：会破坏来源关系和打包历史，不能满足追溯目标。
- 将 RC Tag 重命名为正式 Tag、沿用 RC 编号：不符合正式版独立递增和同 RC 多次晋升的需求。
- 仅保存 SHA 后删 Tag：不能证明代码始终可拉取，也不适配现有打包流程。
- 自动清理与独立源码归档：引入额外策略和存储责任，本期不采用。
