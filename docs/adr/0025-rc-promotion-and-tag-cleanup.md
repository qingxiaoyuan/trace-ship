# 0025 - 正式发布固定来源 RC，标签清理与发布历史分离

## Status

accepted，2026-10-09。用户已确认[规格 #5](https://github.com/qingxiaoyuan/trace-ship/issues/5)的建议基线与测试边界。决策接受不代表全部实现；实施与验收按关联任务 #12–#18 推进。

## Context

2026-10-22 范围调整：用户在 [事项 #52](https://github.com/qingxiaoyuan/trace-ship/issues/52) 确认暂缓正式版必须从 RC 检出的规则，当前新建正式版恢复选择分支，服务端固定创建时提交。正式审批、版本占用、推 Tag 核验和清理保护继续生效；已存 RC 来源与累计说明保留兼容处理。以下 RC 晋升设计保留为历史及兼容语义，不再要求所有新正式版具备 RC 来源。

同日审查修复：分支来源须经分支专用接口确认并保存完整 HEAD，不能使用 Tag、SHA 或提交范围替代。所有正式版的说明和关联变更均按保存的提交完整收集，来源或目标版本变化后失效并要求重新生成；说明的版本与提交身份由系统维护，保存和提审时复核。存量已发布且未初始化快照的说明继续兼容原编辑方式。

同日 [事项 #53](https://github.com/qingxiaoyuan/trace-ship/issues/53) 明确发起人可终止任意运行中的审批。沿用实例 `revoked` 与发布回到草稿的语义，待办任务增加 `revoked` 失效状态，已处理历史保留。审批和终止共用仓库 → 发布 → 实例锁顺序，并在锁内读取当前状态，确保最后审批与终止只有先获得锁的一方能决定终态；已结束实例不再撤回。

正式发布需基于测试过的 RC 代码，但继续采用独立的正式版本号；同一 RC 可以产生多个正式版。RC 标签积累需要手动清理，而现有源码获取依赖标签，平台删除版本还可能级联删除打包历史。

## Decision

采用固定提交与来源快照表达正式版的代码身份，将远端标签生命周期与平台发布记录生命周期分离。清理只移除标签，保留来源关系；通过仍存在且提交一致的正式引用获取已清理 RC 的代码，执行构建前核验提交。

版本归属继续遵守 ADR-0020 的物理仓库边界，名称使用 ADR-0021 的项目口径。审批和打包继续使用既有模块与独立生命周期。

按本决策实施时，ADR-0015 的标签删除能力增加跨入口引用保护；其“版本计算仅依赖远端”的前提改为同时保留已发布历史编号依据。正式版标签与 RC 标签不做重命名替换。

正式累计说明以提交身份定义区间：基线是同物理仓库中低于目标正式版本且在来源祖先链上的最高正式版本，平台已发布历史快照优先于同名远端 Tag；首次生成后冻结基线名称与 SHA。首发累计全部可达历史，同 SHA 允许无新增代码，非祖先候选按版本号递减继续查找可达 Tag，无可用基线时按全部可达历史生成并明确提示。GitLab 提交接口按 revision range 完整分页；MR 仅以区间内的合并或 squash 提交作为纳入证据，证据缺失显示提示，外部故障不伪装成空区间。人工说明不改变系统身份。

2026-11-02 维护分支兼容修复（[#83](https://github.com/qingxiaoyuan/trace-ship/issues/83)）：创建与编辑统一以手工填写的最终 Tag 确定发布版本号；不能保留客户端同时传入的旧自动建议版本。上次发布为 master 的 5.9.4，维护分支 a 的 Tag 为 5.2.39，本次 Tag 为 5.2.40 时，按 5.2.39 至 a 的固定提交生成说明。旧正式草稿的版本号与 Tag 不一致时，预览按 Tag 计算候选区间且不写库；生成时在原事务内修正版本号、清除旧派生内容并重新固定基线，失败整体回滚。已一致的基线继续冻结，不改变已提审/已发布身份；祖先链保护仍保留，错误提示补充实际基线、目标 Tag、提交和分支，便于内网定位。

2026-11-02 用户追加基线回退规则（[#85](https://github.com/qingxiaoyuan/trace-ship/issues/85)）：5.2.40 的 5.2.39 不可达时继续查找 5.2.38 等更低的可达正式版本；说明保存跳过候选及实际基线。正常固定基线和回退理由保持不变，旧草稿已有非祖先基线时预览只读重算、生成事务内重建；已进入流程或已发布的基线不自动修改。每个候选按完整 SHA 核验，平台历史同名快照优先于远端，同版本多个可达 SHA 仍要求核对。没有可达候选沿用无基线全历史范围，接受说明可能更长；查询失败仍明确失败，不伪装成空区间。此规则替代旧版“遇到分叉直接拒绝生成”的处理，实际发布 SHA、审批及版本占用不变。

版本占用以物理仓库、发布类型、主次修订号唯一，不包含日期和项目；成功后保留已消费记录，审批终止释放，推 Tag 失败保留供重试。迁移仅为当时已经进入审批的历史正式申请设置可信兼容标记，客户端不能写入该标记。

2026-11-02 删除语义调整（[#83](https://github.com/qingxiaoyuan/trace-ship/issues/83)）：用户需要在误发版本后明确删除发布记录和 Tag，再重新发布同一编号。成功执行「删除版本」时，在既有仓库锁和引用保护下同步释放该申请的占用；仅清理 Tag、保留发布记录时继续保留编号。旧版删除留下的已消费孤立占用不再抬高自动编号，重新提审时只有在实时远端查询成功、同仓库同类型无同版本 Tag 且无其他有效发布占用的情况下才可重新取得；仍按规范化编号检查日期与跨项目冲突。仓库前缀或类型后缀变更后，复用前仍核验原占用记录指向的 Tag，并将其有无日期及不同日期形式视为同一版本，不能把当前规则无法识别当作远端不存在。主次修订号按整数匹配，前导零不划分占用；复用只转移申请归属，不覆盖原 Tag 身份，提审、推送和重试持续核验。占用增加默认关闭的历史复用标记，取得旧孤立占用时设置；终止复用申请时按该标记恢复原孤立占用，避免同名重发被误判为新占用而丢失旧身份依据。迁移只新增标记，不批量清除或转移历史占用。查询或删除结果不明保持失败，不批量删除历史占用，不覆盖现存 Tag。重发重新走审批，删除操作日志继续保留。

2026-11-03 旧规则历史冲突修复（[#87](https://github.com/qingxiaoyuan/trace-ship/issues/87)）：现行规则及占用保存的原 Tag 身份统一用于远端 Tag 和平台有效发布记录检查。旧记录不符合新前缀或类型后缀时，仍按原身份及规范化编号参与冲突判断；同仓库同类型的已发布、在审及审批完成但推送失败记录继续占号，跨项目、日期和前导零不能绕过。提审、推送与重试共用核验；没有有效冲突时保留旧占用复用及终止恢复语义。本次无迁移，不清理历史数据。

2026-11-03 多次规则变更补充（[#89](https://github.com/qingxiaoyuan/trace-ship/issues/89)）：平台有效发布按每条记录自身的 Tag 解析规范化编号，不再受当前规则和唯一孤立占用的两套身份限制。保存的纯版本号只帮助辨认前缀边界；版本数字不一致时仍以 Tag 为准。前后缀可包含数字、点和连字符，不能直接截取第一组或最后一组数字；没有可用边界且多个候选编号涉及目标版本时明确拒绝，要求核对该条历史身份，不猜测编号也不改写历史记录。无歧义旧记录（包括版本号含旧后缀的记录）继续兼容。远端 Tag 仍按当前规则及原占用身份核验，终止恢复与删除语义不变，无新增迁移。

2026-10-22 兼容调整（[#57](https://github.com/qingxiaoyuan/trace-ship/issues/57)）：用户在同一内网 GitLab 账号下确认网页空 Message 创建成功、填写 Message 创建失败。发布新建恢复轻量 Tag，按固定 SHA 创建但不传注释，避免所有发布类型共用的注释参数触发故障。历史注释 Tag 仍以本申请标记和 SHA 共同作为未知结果对账证据；轻量 Tag 缺少这种归属证据，若写入结果不明而重试发现同名 Tag，则保留占用并要求管理员核对，不仅凭同 SHA 自动接管或重建。这一取舍优先恢复内网兼容并保护外部 Tag，代价是轻量 Tag 的未知结果需人工核对。失败操作日志保存受限、脱敏的服务端响应和请求编号，便于内网继续追查 GitLab 服务端异常。

正式发布必须有非空流程和有效审批人；稳定性由配置的人工审批确认。仓库锁统一协调提交、任务创建、引用删除和清理；执行构建前再次核验实际 HEAD，不能用选择候选时的校验替代。远端操作无法与数据库原子提交，清理先写尝试记录再操作，重试区分已确认的平台删除与无法归属的远端缺失。

## Consequences

- Tag 数量可以减少，同时保留审批和代码来源；同 RC 可多次晋升。
- 需要保存来源与清理元数据，保护最后一个有效引用，并处理远端操作与本地记录部分成功。
- 拉取引用与版本显示分开后，自定义打包脚本不能假定已清理的 RC Tag 仍存在；重打包只保证代码提交身份。
- 平台不能阻止所有外部 Tag 改写，必须在后续使用时重新验证。

## Alternatives

- 永久保留所有 RC Tag：实现最少，但不能解决用户提出的标签管理问题。
- 删除 RC 发布记录与 Tag：会破坏来源关系和打包历史，不能满足追溯目标。
- 将 RC Tag 重命名为正式 Tag、沿用 RC 编号：不符合正式版独立递增和同 RC 多次晋升的需求。
- 仅保存 SHA 后删 Tag：不能证明代码始终可拉取，也不适配现有打包流程。
- 自动清理与独立源码归档：引入额外策略和存储责任，本期不采用。
