# 0025 - 正式发布固定来源 RC，标签清理与发布历史分离

## Status

proposed，2026-10-09。用户已确认主要产品方向；本文的引用保护及兼容细节待随[规格](https://github.com/qingxiaoyuan/trace-ship/issues/5)整体审阅。

## Context

正式发布需基于测试过的 RC 代码，但继续采用独立的正式版本号；同一 RC 可以产生多个正式版。RC 标签积累需要手动清理，而现有源码获取依赖标签，平台删除版本还可能级联删除打包历史。

## Decision

拟采用固定提交与来源快照表达正式版的代码身份，将远端标签生命周期与平台发布记录生命周期分离。清理只移除标签，保留来源关系；通过仍存在且提交一致的正式引用获取已清理 RC 的代码，执行构建前核验提交。

版本归属继续遵守 ADR-0020 的物理仓库边界，名称使用 ADR-0021 的项目口径。审批和打包继续使用既有模块与独立生命周期。

本决策接受后，ADR-0015 的标签删除能力增加跨入口引用保护；其“版本计算仅依赖远端”的前提改为同时保留已发布历史编号依据。正式版标签与 RC 标签不做重命名替换。

## Consequences

- Tag 数量可以减少，同时保留审批和代码来源；同 RC 可多次晋升。
- 需要保存来源与清理元数据，保护最后一个有效引用，并处理远端操作与本地记录部分成功。
- 拉取引用与版本显示分开后，自定义打包脚本不能假定已清理的 RC Tag 仍存在；重打包只保证代码提交身份。
- 平台不能阻止所有外部 Tag 改写，必须在后续使用时重新验证。

## Alternatives

- 永久保留所有 RC Tag：实现最少，但不能解决用户提出的标签管理问题。
- 删除 RC 发布记录与 Tag：会破坏来源关系和打包历史，不能满足追溯目标。
- 将 RC Tag 重命名为正式 Tag、沿用 RC 编号：不符合正式版独立递增和同 RC 多次晋升的需求。
- 仅保存 SHA 后删 Tag：不能证明代码始终可拉取，也不适配现有打包流程。
- 自动清理与独立源码归档：引入额外策略和存储责任，本期不采用。
