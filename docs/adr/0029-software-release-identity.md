# 0029 - 以软件作为跨项目复用的发布与版本主体

**状态:** accepted（软件登记、维护授权和项目选用见 #112）
**日期:** 2026-11-16
**关联规格:** [#111 按软件独立管理发布版本并支持跨项目复用](https://github.com/qingxiaoyuan/trace-ship/issues/111)

同一仓库可以产出多个独立演进的软件。若继续以仓库作为唯一版本主体，软件 A 和软件 B 各自发布同类型的 `2.1.0` 时，会被视为同一版本；若以打包配置作为软件身份，又会把同一软件的不同平台包拆成不同软件。因此引入独立的软件身份，承载软件的发布和版本历史。

## 已确认的领域边界

1. 一个软件以一个主仓库为发布源码来源，一个仓库可以包含多个软件；现有 Git 子模块仍可随主仓库构建，本次不引入多仓库组合发布。
2. 软件使用仓库内唯一的稳定标识，显示名称可以改变，身份和版本历史保持不变。
3. 项目是组织软件的分组，显式选用软件；不同项目可选择同一仓库中的不同软件，也可复用同一个软件。软件跨项目共享身份和版本历史，项目不产生独立版本或额外的软件发布生命周期。
4. 打包配置直接归属于软件，由选用该软件的项目共同使用；同一软件可以有多个平台或交付方式的配置，共享软件版本序列。
5. 一次发布只针对一个软件，确定该软件的源码提交和版本，只自动触发该软件本次选中的打包配置。
6. 新的软件 Tag 使用“软件标识/版本 Tag”，后半段保留现有版本格式及正式、RC、Beta、日期规则，例如 `client-a/v2.1.0` 与 `server-b/v2.1.0`。显示名称、项目名称和打包配置名称不参与 Tag 命名；版本占用与历史查询也按软件区分。
7. 软件版本已经发布后，其他选用该软件的项目可以复用该版本及固定源码进行打包，不重新创建相同的软件版本或 Tag；已有版本绑定的源码保持不变。
8. 项目继续承载现有成员、角色和数据可见范围；“项目只是分组”指发布流程不按项目产生另一套版本或增加项目审批，不表示取消权限边界。
9. 软件发布继续使用主仓库现有的审批流程模板，每次软件发布分别产生审批记录；本次不改成各软件独立配置流程，也不增加项目审批层级。
10. 存量 Tag 保留原名，原审批和产物记录保持原样，由负责人确认历史发布的软件归属；无法确定的保留为待归属的仓库历史。新发布使用软件前缀，不根据打包配置名称猜测历史软件身份。
11. 软件设置维护负责人，默认主仓库所有者，并可授权协作维护者，负责维护软件资料和共享打包配置；项目管理员或项目软件管理员身份本身不自动获得共享配置修改权。软件的使用操作继续遵循项目角色权限。
12. 软件版本跨项目共享，但打包任务、日志和产物按发起项目授权；选用同一软件不会自动获得其他项目构建记录或产物的访问权限。

## 与现行模型的关系

这是对 [ADR-0020](0020-product-repository-composition.md) 中“版本属于仓库”的目标调整，软件登记与项目选用已接入，现有仓库发布路径及历史记录含义沿用原规则。保留物理仓库复用与项目上下文的概念，将独立版本主体细化到软件；项目自身仍不产生组合版本。

源码版本文件的自动读取与校验已暂缓讨论，不属于本次已确认的架构范围。本 ADR 记录版本管理的领域边界，改造范围、业务约束、测试边界与验收条件统一维护在规格 #111；具体接口与迁移编排由后续实施任务细化。


## 软件登记与项目选用

- 仓库所有者或超管可以在主仓库下登记软件。软件标识为使用短横线分隔的小写英文字母、数字组合，最多 80 个字符。同一主仓库内唯一，标识和主仓库在登记后固定；显示名称和说明可更新。旧仓库没有创建者时，沿用其个人凭证所有者认定。
- 软件维护负责人默认是主仓库所有者，可授权、撤销软件协作维护者，也可移交负责人或启停软件。超管可执行同样操作。协作维护者通过独立软件目录更新资料，项目成员角色与软件维护职权分别校验。
- 项目管理员或项目软件管理员可从该项目已启用的主仓库中选用软件。项目需满足既有仓库所有者入项规则。软件停用及项目停止选用均保留原身份或关联；历史选用允许项目成员查阅。
- 软件停用和选用状态变更使用主仓库锁。新增软件业务操作在同一锁下核验最新选用与启用状态、目标项目角色以及仓库所有者入项前提。用于历史读取的关联仍保留。
- 有软件身份的主仓库、有软件选用记录的项目，以及该项目最后一个供该软件引用的仓库组件，暂保留删除保护，直到对应历史与业务引用的删除规则全部接入。
