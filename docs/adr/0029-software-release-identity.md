# 0029 - 以软件作为跨项目复用的发布与版本主体

**状态:** accepted
**日期:** 2026-11-16
**关联规格:** [#111 按软件独立管理发布版本并支持跨项目复用](https://github.com/qingxiaoyuan/trace-ship/issues/111)

同一仓库可以产出多个独立演进的软件。若继续以仓库作为唯一版本主体，软件 A 和软件 B 各自发布同类型的 `2.1.0` 时，会被视为同一版本；若以打包配置作为软件身份，又会把同一软件的不同平台包拆成不同软件。因此引入独立的软件身份，承载软件的发布和版本历史。

## 已确认的领域边界

1. 一个软件以一个主仓库为发布源码来源，一个仓库可以包含多个软件；现有 Git 子模块仍可随主仓库构建，本次不引入多仓库组合发布。
2. 软件使用仓库内唯一的稳定标识，显示名称可以改变，身份和版本历史保持不变。
3. 项目是组织软件的分组，显式选用软件；不同项目可选择同一仓库中的不同软件，也可复用同一个软件。软件跨项目共享身份和版本历史，项目不产生独立版本或额外的软件发布生命周期。
4. 打包配置直接归属于软件，由选用该软件的项目共同使用；同一软件可以有多个平台或交付方式的配置，共享软件版本序列。
5. 一次发布只针对一个软件，确定该软件的源码提交和版本，只自动触发该软件本次选中的打包配置。
6. 新的软件 Tag 使用“软件标识/版本 Tag”，后半段保留现有版本格式及正式、RC、Beta、日期规则，例如 `client-a/v2.1.0` 与 `server-b/v2.1.0`。显示名称、项目名称和打包配置名称不参与 Tag 命名；版本占用与历史查询也按软件区分。
7. 软件版本已经发布后，其他选用该软件的项目可以复用该版本及固定源码进行打包，不重新创建相同的软件版本或 Tag；已有版本绑定的源码保持不变。
8. 项目继续承载现有成员、角色和数据可见范围；“项目只是分组”指发布流程不按项目产生另一套版本或增加项目审批，不表示取消权限边界。
9. 软件发布继续使用主仓库现有的审批流程模板，每次软件发布分别产生审批记录；本次不改成各软件独立配置流程，也不增加项目审批层级。
10. 存量 Tag 保留原名，原审批和产物记录保持原样，由负责人确认历史发布的软件归属；无法确定的保留为待归属的仓库历史。新发布使用软件前缀，不根据打包配置名称猜测历史软件身份。
11. 软件设置维护负责人，默认主仓库所有者，并可授权协作维护者，负责维护软件资料和共享打包配置；项目管理员或项目软件管理员身份本身不自动获得共享配置修改权。软件的使用操作继续遵循项目角色权限。
12. 软件版本跨项目共享，但打包任务、日志和产物按发起项目授权；选用同一软件不会自动获得其他项目构建记录或产物的访问权限。

## 与现行模型的关系

本决策替代 [ADR-0020](0020-product-repository-composition.md) 中“版本属于仓库”的规则，保留物理仓库复用、项目权限和历史记录。新建发布和打包配置均须指定软件；已经存在的仓库草稿与在途审批、旧 Tag、待归属历史和旧配置继续按原权限处理。

源码版本文件的自动读取与校验已暂缓讨论，不属于本次已确认的架构范围。本 ADR 记录版本管理的领域边界，改造范围、业务约束、测试边界与验收条件统一维护在规格 #111；具体接口与迁移编排由后续实施任务细化。


## 软件登记与项目选用

- 仓库所有者或超管可以在主仓库下登记软件。软件标识为使用短横线分隔的小写英文字母、数字组合，最多 80 个字符。同一主仓库内唯一，标识和主仓库在登记后固定；显示名称和说明可更新。旧仓库没有创建者时，沿用其个人凭证所有者认定。
- 软件维护负责人默认是主仓库所有者，可授权、撤销软件协作维护者，也可移交负责人或启停软件。超管可执行同样操作。协作维护者通过独立软件目录更新资料，项目成员角色与软件维护职权分别校验。
- 项目管理员或项目软件管理员可从该项目已启用的主仓库中选用软件。项目需满足既有仓库所有者入项规则。软件停用及项目停止选用均保留原身份或关联；历史选用允许项目成员查阅。
- 软件停用和选用状态变更使用主仓库锁。新增软件业务操作在同一锁下核验最新选用与启用状态、目标项目角色以及仓库所有者入项前提。用于历史读取的关联仍保留。
- 有软件身份的主仓库、留有软件选用记录的项目，以及该项目最后一个供该软件引用的仓库组件受删除保护。


## 历史发布归属确认与切换

在完成数据库迁移后，可在后端用 `python manage.py assign_software_release_history` 生成只读 JSON 盘点。使用 `--repository <主仓库 UUID>` 缩小范围。报告列出发布、存量版本占用、缓存 Tag、打包配置与任务快照的关联标识，以及 OA 和 Tag 清理保护引用。缓存 Tag 附带更新时间。报告明确列出重复编号、存量同名配置、关联任务指向多个软件及历史版本或源码证据缺口。

确认表是 JSON 数组，每项提供原发布 UUID、目标软件 UUID 和实际核对依据。软件维护负责人确认各发布，涉及多软件、同名配置或来源不完整时先核对原审批与交付证据。使用实际确认人的登录名预检，获授权后才执行第二条命令。

```json
[
  {
    "release": "00000000-0000-0000-0000-000000000001",
    "software": "00000000-0000-0000-0000-000000000002",
    "basis": "核对原审批单与对应的交付说明"
  }
]
```

```bash
python manage.py assign_software_release_history --mapping confirmed.json --confirmed-by <实际登录名>
python manage.py assign_software_release_history --mapping confirmed.json --confirmed-by <实际登录名> --apply
```

实际确认事务先按主仓库顺序加锁，再核对原 Tag 或同一来源链的有效等价引用及完整 SHA。一个批次存在冲突时保留报告，整批不写入。仅为明确的已发布历史附加软件、唯一基础版本、确认人、时间和依据。旧 Tag、占用、审批、说明、任务、产物和 OA 快照沿用原记录。重放同一归属返回已有结果。前后报告记录数量、关系、说明摘要校验值和保护引用，可据此复核。未确认的记录按旧项目权限读取。

打包配置使用 `python manage.py reconcile_package_configs` 盘点；确认表包含 `config`、`software`、`projects` 和 `basis`，格式见 [打包 API](../api/api-spec.md#96-打包配置列表与维护)。`--mapping <文件> --actor <登录名>` 先预检，再经确认追加 `--apply`。原配置 ID 和历史任务保留，旧在途发布引用的配置须先处理。两类确认分别提交，各自批次有阻断时整批不写入。

在隔离副本按以下顺序演练切换：

1. 保存业务库备份，对照原版本的 `python manage.py check_product_repository_consistency --json --strict` 报告及各表数量，记录原 Git Tag 与完整 SHA。应用数据库结构迁移后，确认旧资源仍用原 ID 和旧项目权限读取。
2. 登记软件和明确选用项目；导出归属盘点，保存确认表和 dry-run 报告。另留同名配置、归属或源码不明、重复编号样本，核对它们是否明确列出且没有被自动合并。
3. 只对证据明确并已有授权的项目范围分别确认发布和配置。保留确认前后报告，用原确认表再执行一次核对幂等；比较原 Tag、审批、说明、任务、产物及 OA 保护。验证选用项目只新增确认后的已发布版本读取，其他项目的日志、产物和 OA 数据仍隔离。
4. 新建页面与 API 一律显式选择软件。保留旧详情和草稿深链、旧在途审批路径以及未归属历史；`ProjectComponent` 继续承载仓库关联，不充当软件身份。

## 软件版本复用与引用保护

- 发布选择本软件启用的自动配置，发布成功后只为原发起项目触发选中且仍可用的配置。旧仓库版本保留配置选择为空值时的历史自动触发规则。
- 手动复用显式指定选用项目和软件，按该项目授权创建独立任务。重试保存原任务引用，复用完整源码、Tag、版本与配置快照，按当前实际操作者、项目选用及凭证重新授权。停止选用或停用配置挡住新任务，已排队任务继续按快照执行。
- 共享版本的构建从完整 Git Tag 引用拉取，在各执行器核验实际 SHA 后运行构建脚本。已确认归属的旧 Tag 仍使用原名。脚本的 Tag、版本和说明路径保持各自含义。
- 原发起项目按既有权限办理删除发布或清理 RC Tag。持仓库锁核验同名历史、固定提交、跨项目在途任务、最后源码引用和 OA 保护。删除项目还持有当前仓库及项目锁，核验将被级联触及的任务。停止选用、停用项目和停用配置保留历史记录。
- 软件已发布版本的说明、导出、通知和 OA 来源使用发布时的身份和完整 SHA。软件显示名可在目录改动；旧说明、任务快照及归档副本保持原名。归档目录与历史按实际任务项目授权。
